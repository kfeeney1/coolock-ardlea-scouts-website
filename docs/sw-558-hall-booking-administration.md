# SW-558 Council booking administration

`/leader/hall` lists bounded pages of private bookings; `/leader/hall/new` creates a booking and `/leader/hall/:bookingId` opens an existing record. A Dashboard button appears for current Council members only while Hall Hire is enabled and server readiness is true. The shared CalendarPageLayout preserves Group branding, theme tokens and the real leader navigation in both existing/redesigned modes. Routes remain independently protected; the Worker rechecks authoritative Council appointments on every request.

Internal, external and blocked bookings use the single canonical hall record. Drafts do not reserve time; confirmed records do; cancellation releases occupancy without deleting history. Private details include title, hirer/group, contact and leader notes. Source-owned reservations remain read-only here and must be changed through their original record.

Weekly bookings have a bounded Repeat until date. Existing series explicitly select Entire series or One occurrence. Occurrence cancellation/rescheduling retains other exceptions. Moving an entire series shifts exception identities and replacement dates by the same day offset; invalid new recurrence bounds are rejected instead of dropping exceptions. Restore series time removes a selected exception in the pending editor. Whole-series cancellation is explicit and retains records. Ambiguous/missing Dublin clock-change times and overlapping intervals are rejected by shared validation and the authoritative writer.

The editor reuses the site date picker and Save/Discard/Stay leave guard. Invalid date text cannot silently save a previous valid date. Only one save runs at a time; conflicts retain form values and require user review. Writes strip revision/actor/source metadata and send the expected revision separately. The existing backend transport never reads an error response body; error messages shown for conflicts/permissions are fixed public-safe text. Private data is cleared from the rendered workspace when access/identity changes. Current membership dates are re-evaluated locally every minute; backend checks remain authoritative.

History and booking lists have explicit pagination. History displays stored revision, date, lifecycle state and actor UID. No programme/member lookup is granted to resolve an actor name.
