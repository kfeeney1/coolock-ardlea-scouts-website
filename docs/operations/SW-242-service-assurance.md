## Threshold decision

| Metric | Meaningful interpretation |
| --- | --- |
| Reliable bounded usage with matching account, unit and reset window | 70% notice (informational), 85% warning, 95% critical, 100% exhausted. The reader supports Notice at 70%, Warning at 85%, Critical at 95% and Exhausted at 100% only when the observation explicitly identifies a hard cap; allowance/reference consumption stays Critical at 100% |
| No-cost allowance on a billed plan | Percentage may describe allowance consumption, **not service exhaustion or a spending cap**. Do not silently turn a generic reference into an account limit |
| Unknown / null / zero limit, stale usage, mismatched windows | No percentage. Null may mean uncapped in provider API semantics, never zero remaining |
| API rate limits | Use matching short window and provider response/reset/Retry-After; a monthly total cannot establish requests-per-second headroom |
| Backups | Age thresholds above, independent failed-attempt status, verified completion marker and monitoring cadence; no percentage quota |
| Email reputation / delivery | Provider-defined event/error categories, no invented aggregate “health percentage” |
| Domain / credential expiry | Verified expiry and time remaining, not usage percentage |

Configured reference values must be labelled separately from provider-retrieved limits. The Resend snapshot is account evidence at the stated time, not a permanent configured value for the site.

## Practical recovery

1. **Triage:** record UTC time, environment, service, safe error category and affected workflow/release. Check provider status and the matching project's console. Never paste raw tokens, full provider responses or personal records into Jira/logs. Do not replay production mutations to reproduce failure.
2. **Quota/billing:** determine hard quota versus no-cost allowance, period/reset and actual account settings. Reduce the identified source of unnecessary traffic. Preserve functionality/data; do not raise quotas, upgrade, disable billing or delete artifacts/data without a reviewed cost/retention decision. Resume only after a safe read-only check confirms recovery.
3. **Rate limiting:** respect Retry-After/reset and existing bounded handling; stop repetitive manual actions. Inspect burst/concurrency origin. Do not add unbounded retries or duplicate email sends. Verify later with read-only provider evidence.
4. **Email:** confirm active production Worker, route, Firebase project, delivery mode, cron and existing secret presence without reading values. Check Resend domain status, aggregate allowance, API error and delivery/suppression category. A verified domain or configured endpoint is insufficient. Resolve DNS/key/IAM via existing approved configuration; avoid resending messages of uncertain outcome. Any test email requires explicit authorisation.
5. **Backup:** compare execution and freshness records. Failed inspection means unknown backup assurance, not proven deletion. Inspect Actions authentication, bucket IAM, expected timestamp format and completed export marker; fix only the failing dependency. Do not create an export or restore for a read-only check. A protected manual backup/restore remains a separate approved operation. Recheck publication/readback and age, then use the established recovery runbook.
6. **Deployment:** inspect required checks for exact head/merge SHA, TEST deploy/smoke and post-merge guard; never use a different SHA's green result. Identify package registry/action/provider/IAM/index/rules failure. Fix the deterministic cause. PRODUCTION remains protected/manual; document a reviewed release/rollback before action. Do not weaken guard, tests or complexity ceilings.
7. **Stale monitoring:** check observedAt, environment and maxAge/cadence, workflow outcome and publisher readback. Repair existing writer access if necessary. Keep historical failure visible; do not overwrite with Healthy or synthetic zero. A page refresh does not refresh provider evidence. Verify the next existing scheduled run publishes a fresh result.
