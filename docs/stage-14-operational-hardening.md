# Stage 14 operational hardening checklist

This checklist closes the remaining low-risk operational items identified during the Stage 14 architecture and reliability review. It is intentionally separate from public-endpoint anti-abuse work, which requires an explicit Cloudflare/Firebase configuration decision before code is changed.

## Firestore query and index review

The emulator does not reliably reproduce every production composite-index requirement. Before a reporting or operational query is treated as production-ready:

1. Record the collection, filters, ordering and expected result size.
2. Exercise the exact query against a production-compatible Firebase project.
3. If Firestore requires a composite index, add that index to `firestore.indexes.json`; never rely on a console-only index.
4. Re-run the relevant unit, Firestore Rules and Playwright coverage.
5. Keep high-cardinality operational queries constrained by section, status, date range or another bounded selector.
6. Prefer server-side counts or deliberately constrained reads for dashboard totals rather than loading entire collections into the browser.

The currently committed `firestore.indexes.json` remains the source of truth for repository-managed composite indexes. New indexes should be introduced in the same PR as the query that needs them whenever practical.

## Backup and restore drill

The scheduled Firestore export is only a backup once restore has been demonstrated. At least once per release cycle that materially changes persisted data structures, perform a non-production restore drill:

1. Choose a recent successful export produced by the backup workflow.
2. Restore it into a dedicated non-production Firebase project or disposable database environment.
3. Run the live-data provenance and compatibility audits against the restored data.
4. Verify representative records from membership, meetings, events/consent, Adventure Skills and Equipment & Stores.
5. Verify parent/member links and leader role/section assignments remain intact.
6. Run the application smoke path against the restored environment where practical.
7. Record the export used, restore destination, duration, audit result and any manual intervention required.

Never test destructive restore procedures against the live production project.

## Build and release identity

Every deployed build should be traceable back to a repository commit. Until a user-visible release/version surface is added, GitHub Actions run metadata and the deployed commit remain the authoritative build identity.

A future build-identity implementation should expose at least the commit SHA and build timestamp without exposing secrets or environment configuration. It should be generated by CI rather than manually maintained.

## Content Security Policy review

The current hosting CSP is deliberately conservative so Firebase authentication and application resources continue to work. Tightening CSP should be done in a preview deployment first. Any stricter policy must be exercised through:

- public pages;
- leader and parent authentication;
- Firestore reads/writes;
- event-consent public flows;
- email-backed actions;
- both supported visual themes;
- Chromium and WebKit critical paths.

Do not weaken other existing headers merely to make a stricter CSP pass.

## Public endpoint anti-abuse boundary

CORS and Origin checks are browser controls; they are not sufficient protection against scripted abuse. The following public flows need a deliberate abuse-control design before additional production hardening is considered complete:

- Join Us submissions;
- public event-consent responses;
- any unauthenticated endpoint that can trigger email or create Firestore data.

The preferred design should use an externally verifiable challenge or attestation mechanism (for example Cloudflare Turnstile and/or Firebase App Check where appropriate), plus rate limiting and duplicate suppression. Secrets must remain server-side. In-memory Worker counters must not be presented as durable rate limiting.

Because this requires Cloudflare/Firebase configuration, keys/secrets and a rollout decision, it is a natural change boundary: implementation should be made in a dedicated PR after the required external configuration is chosen and available.

## Stage 14 completion rule

Stage 14 can be considered operationally consolidated when:

- architecture and RBAC contracts are current;
- source-complexity regression protection is active;
- deterministic Playwright tooling is pinned;
- Chromium plus compact WebKit critical-path coverage is green;
- Firestore Rules run for security-sensitive persistence changes;
- email Worker entrypoint contracts are directly tested;
- query/index and restore procedures are documented and periodically exercised;
- public unauthenticated submission abuse controls are explicitly implemented and verified, or are tracked as the only external-configuration-dependent remaining hardening item.
